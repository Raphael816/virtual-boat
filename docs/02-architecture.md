# 02. 実装方針と技術構成

## 4. レース表現と結果シミュレーション

### 4.1 基本の考え方：「シミュレーションが正、映像は再生」

- 結果は `core/sim.ts` の決定論的なシミュレーションだけで決まる。同じ（水面条件・出走艇・seed）からは常に同じ結果。
- 3D／2D の映像・実況・解説は、その走行ログ（0.05秒ごとの各艇の位置・横位置・速度）を再生・説明するだけで、結果に影響しない。
- 映像の時刻 0 はスタート合図の 6 秒前（`LEAD`）。大時計の針は合図の瞬間に真上を指す。

### 4.2 シミュレーションモデル

座標は水面の内側の線に沿った距離 `s` と、そこから外側への横の距離 `d`（`core/course.ts`）。

| 局面 | モデル |
|---|---|
| スタート | ST ＝ 平均ST ＋ ばらつき（スタート技術が高いほど小さい）＋ 潮の影響。ST < 0 はフライング、> 1.0 は出遅れで欠場。1〜3コースはスロー（ライン通過時 約17.5m/s）、4〜6コースはダッシュ（約20.6m/s） |
| 直線 | 最高速度 ＝ 基準 ＋ モーター ＋ 伸び − 体重 ＋ 当日のゆらぎ ＋ 潮・風（向きつき）− 波 |
| 1マークの進入 | 先頭が入口の45m手前に来たら、前の艇から順に線を決める。最内（d=2）を狙い、ほぼ並んだ前の艇がいれば外を回る。内側の後ろの艇の前を横切るには「1.5m＋横の差×0.25」以上前に出ている必要がある（足りなければ外を回る＝攻めきれない）。前の艇の少し後ろなら、その後ろについて内を差す |
| ターン | 旋回速度 √(横加速度 × 半径)。横加速度はターン技術とモーター、毎回のターン精度で決まる。出口では技術・波・潮に応じて外へ流れる。江戸川の特徴として、1周目1マークのイン（1・2コース）は流れやすい（推定。係数 1.6） |
| 引き波・接触回避 | 前の艇の真後ろ（25m以内・横2.5m以内）では5%減速。同じ線で6m以内に詰まったら前の艇の速度まで |
| 決まり手 | 1周1マーク後（出口から50m）の先頭が勝てば、進入の線と内側の艇の流れから 逃げ／差し／まくり／まくり差し／恵まれ を判定。それ以外は 抜き |

調整（`TUNE`、`tests/sim.test.ts`）：開催のレースで集計して、1コースの1着率が約46〜48%（全国平均の約55%より低い江戸川の傾向に合わせた目安）、
決まり手は 逃げ 約46%・まくり 約19%・差し 約14%・まくり差し 約12%・抜き 約9%、優勝タイム 1分43秒〜1分52秒、フライング・出遅れはまれ。

### 4.3 公正性：乱数・ログ・監査

- 結果決定用 seed を暗号論的乱数で生成し、`SHA-256(raceId|seed|engineVersion)` を発売開始時に公開。確定後に seed を公開し、画面から再計算できる。
- オッズ推定の確率は公開シード `mc:<i>`（400回、0.1秒刻み）のモンテカルロ法で求め、結果決定用 seed は使わない。Web Worker で計算。
- 投票・締切・結果（欠場艇を含む）・払戻・返還はハッシュチェーンの監査ログに記録。
- エンジンの版（`boat-1.0.0`）が変わったら、保存済みの開催の未確定の券を返還して新しい開催を始める。

### 4.4 3D表現（`render/three/`）

- 水面：法線マップ2枚を流して重ね、空から作った環境光（IBL）を映す。波高で凹凸、潮で模様の流れる向きが変わる。
- 艇：手続き型のハイドロプレーンと選手（艇番の色のカポック・ヘルメット・背番号）。速度で艇首が上がり、ターンで内側へ傾き、波で揺れる。
- 演出：モーターの水しぶき（ターンでは外側へ）、引き波の泡（走った線が残る）、雨、観客の盛り上がり、吹き流し（風向き・風速）、大時計。
- カメラ：スタンド前からの望遠を基本に局面で切り替え、先頭集団の広がりに合わせて画角を決める。高画質ではモーションブラーと被写界深度。
- 画質：低（影なし・しぶき少なめ）／中／高（ポストプロセス）／自動（FPS で段階的に下げる）。WebGL が使えなければ 2D 上空図。

### 4.5 オッズと払戻（パリミュチュエル方式）

- オッズ ＝ プール総額 ×（1 − 0.25）÷ その組み合わせの票数。0.1倍未満切り捨て、最低1.0倍（元返し）。
- 複勝（的中2）・拡連複（的中3）は利益を的中キーの数で等分してから分ける。確定前は幅で表示。
- 他の利用者の票は「市場プール」として模擬（推定確率に人気の偏りと時間で変わるゆらぎ）。締切で確定。
- **返還**：フライング・出遅れの艇を含む組み合わせは返還し、その票をプールから除いてからオッズを計算。完走艇が足りず的中の組み合わせを作れない券種は不成立として全額返還（`pool.ts settleOdds` → `state.ts settleRace`）。

## 5. 技術構成と課題

### 5.1 MVP構成

- Vite + TypeScript、three.js 0.170（3D は動的読み込み）、Vitest、GitHub Actions（型チェック・テスト・ビルド、Pages は変数で有効化）。
- ハッシュルーターの SPA。状態は localStorage（`virtual-boat:v1`）。

### 5.2 本番を想定した構成（将来）

- 結果の計算・seed 管理はサーバー側（KMS/HSM）。クライアントは走行ログを受け取って再生するだけにする。
- 監査ログは WORM ストレージ、投票は冪等なAPIと複式簿記の台帳。

### 5.3 性能・運用上の課題

- 1レースの公式計算は約5ms、確率推定は約0.6秒（Worker）。
- モバイルの3Dは低画質から開始。水面のシェーダーとしぶきの粒子数が主な負荷。
